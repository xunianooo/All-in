⏳ 临时拒绝后的等待与流式保活

有什么用：供应商临时忙碌时，允许网关多等一会儿再尝试；流心跳则在流式等待期间发送很小的保活信号，帮助部分客户端保持连接。两项可分别设置。

什么时候需要：经常遇到短暂限流、服务器忙，且愿意用更长等待换取成功机会时，可尝试额外等待，例如 10000 毫秒（10 秒）。只有客户端因连接空闲而断开时，才考虑开启心跳。日常使用建议保持默认关闭。

会有什么影响：额外等待可能让报错变慢；心跳不会让模型更快生成，也不保证避免客户端超时。它们不替代供应商自身的自动兼容与重试处理；关闭这里不会关闭 WorkBuddy、ZCode 已有的自动处理。

默认关闭。先尝试可用备选，只有明确的短暂限流或过载拒绝才可等待后重试；额度、鉴权、小浣熊账号吞吐墙、代理与执行结果未知不进入耐受重试。等待和重试仍受总尝试次数与请求截止时间约束。

心跳约3秒一次，仅适用于标准 Chat / Messages / Responses 流式接口，完整事件之间发送注释，不算业务进度或 Token。上游半个事件停顿时不能插入。首个心跳之后 HTTP 状态已提交，后续失败通过协议错误返回。并非所有客户端的业务超时都会被心跳重置。

🚦 请求限速与排队

有什么用：给本机发往供应商的请求主动“限速”和“排队”，避免多个客户端同时调用时一下子发出太多请求。这是手动设置的本机上限，不会自动查询厂商套餐，也不会增加额度。

什么时候需要：已知 API 有明确的每分钟请求数或并发上限，或多个客户端共用同一账号且频繁触发限流时。普通使用建议保持间隔、请求数、同时处理数均为 0（不限）。供应商专用通道已有的自动并发保护独立生效，无需在这里重复设置。

怎么填写：供应商 ID 可在供应商页面查看，例如 raccoon。“每个凭据独立”表示每个账号或 API Key 分别计数，同一凭据调用不同模型会共用限额；“整个供应商共享”表示全部凭据合计，两种限制可同时生效。

参数示例：间隔 1000 毫秒表示两次发送至少隔 1 秒；滚动 60 秒请求数 20 表示任意连续 60 秒最多发送 20 次；同时处理数 2 表示最多两条请求正在执行（流式请求直到结束才释放）。排队数和排队时间限制等待位置及等待时长，不是模型生成超时。

会有什么影响：限制越紧，等待越久；队列满或等待到期可能被拒绝。设得过低会拖慢正常调用。这不是消费金额、Token 预算或厂商额度管理。

按真实凭据跨模型共用限额，可叠加供应商共享限额。默认不限制发送频率或并发。当前覆盖普通商业 Chat / Anthropic / Responses 和小浣熊推理；登录、刷新、目录查询及其它特殊通道不在此范围。参数是本机策略，不代表厂商官方限额。

间隔、RPM、在途数为 0 表示不限。排队参数为 0 时仍受网关总队列与请求截止时间约束。优先选择可立即发送的可用备选；取消、超时或服务停止会退出等待。

🔗 同一会话优先沿用账号

有什么用：同一段对话后续调用时，尽量沿用上一次成功使用的供应商和账号/API Key，减少在多个账号之间来回切换。它不会替你保存聊天记录，也不会把对话同步给其它客户端。

什么时候需要：商业 API 配置了多个账号或 Key，客户端又会发送固定的会话标识，并且希望同一对话尽量走同一路径时。只有一个账号、使用订阅/gift 通道或客户端不传会话标识时，通常没有必要开启。默认关闭，正常路由仍会自动运行。

会有什么影响：请求可能更集中到同一个账号；遇到冷却、禁用或限额时仍优先保障可用性，不会强行绑定。不能保证缓存命中或减少费用。支持的会话请求头包括 x-magpie-session、x-claude-code-session-id、x-session-id、session_id、x-conversation-id；网关不会从聊天内容猜测会话。

默认关闭。客户端提供明确会话标识时，成功交付后尽量沿用商业供应商与凭据。冷却、禁用、移除或出站限制优先，手动路由优先；不同会话仍按原策略分流。进程重启和配置变化会清空绑定，不保证厂商缓存命中。

只使用显式会话请求头，不从提示词推断。绑定保存在有界进程内存中，默认30分钟有效，首次请求预约最长60秒；容量不足时保可用性。订阅、gift及未覆盖特殊通道不承诺绑定。

🔀 虚拟模型路由组

一个路由组就是一个「虚拟模型」，客户端填 group/组id 就能用。 成员从已入池且已同步模型的供应商里挑，顺序由你决定； 前一个调不动会自动换下一个，客户端看不到报错。

仅影响不带 provider/ 前缀的模型：找不到已列出的模型时，开启后尝试第一家配置了密钥的供应商。关闭时返回错误；provider/model 和 group/组id 的路由不受影响。

路由组当前关闭：客户端请直接填 provider/model 自由选择模型； group/* 的请求会被拒绝（403）。需要用时把上面的开关打开。

四种策略
order：按你排的顺序，第一个一直用到调不动为止（主备思路，最省额度）
rotate：每个请求轮到下一个成员（多账号摊平，避免单个账号被限流）
manual：选中项优先，其余兜底（手动切线路）
近期用量优先：优先选择近期可信用量与在途负载较低的目标，失败仍按原规则回退

🧩 网关中间件

中间件作用在每一个请求和每一条回复上，与用哪家供应商无关。 任何一项出错都会原样放行，不会让请求失败。

think-tags
国产模型常把思维链混在正文里。strip 把 <think>…</think> 挪进 reasoning_content（正文更干净）；toContent 反过来，把 reasoning 包成 <think> 塞回正文（给不认 reasoning 的客户端看）。
word-guard 敏感词
同时扫用户发送的内容与模型回复。注意这与「隐私脱敏」不同： 脱敏是保护你的凭据不外发，这里是按词表拦截或打码。
其它三项
model-map：别名 → 真实模型，回复仍报你请求的名字。
param-override：统一参数 / 给 max_tokens 封顶。
system-prompt：每次请求都注入统一的 system 提示。

请检查通知与后台设置。部分厂商选项无法自动读取，手动确认不等于系统验证。
系统定时自检请求间隔约 15 分钟，系统可能延迟执行；进程内自检间隔约 30 秒，冻结期间线程也不运行。无法保证所有 ROM 永不掉线。
